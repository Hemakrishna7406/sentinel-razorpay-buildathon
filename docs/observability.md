# Sentinel Observability Contract

**Status:** Frozen — Phase 21  
**Phase 20 baseline:** ~327 RPS · ~346 ms p99 · 100 CC · 1 worker · MAX_CONCURRENT_TASKS=2 · XGB_NTHREAD=4

---

## Guiding Principle

> Observability is strictly out-of-band. Metrics, logs, and traces are passengers on the authorization path — they observe decisions but never participate in them. If any observability component fails, authorization continues unchanged and fail-closed.

---

## 1. Correlation ID Chain

Every intent that enters Sentinel produces a traceable chain of identifiers:

```
intent_id          — set by the caller at POST /evaluate
  │
  ├── agent_id     — identifies the autonomous agent
  │
  ├── decision_id  — evaluation UUID (generated by evaluator worker)
  │
  ├── capability_jti — JWT ID of the capability token (if ALLOW)
  │
  ├── execution_id — downstream payment provider reference (if executed)
  │
  └── audit_record_id — immutable ledger row ID
```

The `intent_id` is the primary correlation key. Every structured log line, every trace span, and every metric label that can carry it, must carry it.

## 2. Metric Definitions

### 2.1 Authorization Metrics

| Metric | Type | Labels | Description |
|---|---|---|---|
| `sentinel_intents_total` | Counter | — | Total intents received at `/evaluate` |
| `sentinel_decisions_total` | Counter | `decision`, `reason` | Decisions by outcome and reason code |
| `sentinel_authorization_latency_seconds` | Histogram | — | End-to-end `/evaluate` latency (API side) |
| `sentinel_risk_score` | Histogram | — | Distribution of final fused risk scores |

**`decision` label values:** `ALLOW` · `ESCALATE` · `CONTAIN`

**`reason` label values (key subset):**

| Reason | Meaning |
|---|---|
| `RISK_TOO_HIGH` | Model/fusion score exceeded threshold |
| `MODEL_UNAVAILABLE` | XGBoost not loaded; fail-closed |
| `REDIS_UNAVAILABLE` | Idempotency/idempotency check failed |
| `KAFKA_UNAVAILABLE` | Publish to inbound topic failed |
| `POLICY_ENGINE_UNAVAILABLE` | Policy engine threw |
| `CAPABILITY_SIGNING_FAILED` | Token issuer failed |
| `MCP_UNAVAILABLE` | MCP adapter unreachable |
| `EXECUTION_UNKNOWN` | Downstream returned UNKNOWN |
| `IDEMPOTENCY_CONFLICT` | Duplicate key / behavioral duplicate |
| `DEPENDENCY_FAILURE` | Generic dependency unavailable |
| `NORMAL` | Standard authorized request |

| `sentinel_worker_processing_seconds` | Histogram | — | Time inside sync_eval (CPU-bound) |

### 2.3 Dependency Metrics

| Metric | Type | Labels | Description |
|---|---|---|---|
| `sentinel_redis_latency_seconds` | Histogram | `operation` | Per-operation Redis latency |
| `sentinel_postgres_latency_seconds` | Histogram | `operation` | Per-operation Postgres latency |
| `sentinel_kafka_publish_latency_seconds` | Histogram | — | Kafka producer `send_and_wait` latency |
| `sentinel_ml_inference_latency_seconds` | Histogram | `backend` | XGBoost predict latency (cpu/gpu) |
| `sentinel_redis_errors_total` | Counter | `operation` | Redis errors |
| `sentinel_postgres_errors_total` | Counter | `operation` | Postgres errors |
| `sentinel_kafka_errors_total` | Counter | `operation` | Kafka errors |
| `sentinel_ml_errors_total` | Counter | — | ML inference errors |

### 2.4 Security Invariant Metrics

> These counters **must always be zero** in a correctly operating system. Any non-zero value is an operational emergency.

| Metric | Type | Description | Target |
|---|---|---|---|
| `sentinel_security_unauthorized_execution_total` | Counter | Executions without a valid capability token | **= 0** |
| `sentinel_security_duplicate_execution_total` | Counter | Duplicate financial executions | **= 0** |
| `sentinel_security_unsafe_allow_total` | Counter | ALLOW issued when a dependency was unavailable | **= 0** |
| `sentinel_security_token_rejection_total` | Counter | Capability token validation failures | Monitor |
| `sentinel_security_reconciliation_pending` | Gauge | Idempotency keys in PUBLISH_UNKNOWN / UNKNOWN state | **= 0** |

**The authoritative source of truth** for these counters is the PostgreSQL `audit_ledger`. In-process counters are supplementary. On restart, the process may query the ledger to re-seed counter values.

## 3. SLOs (Derived from Phase 20 Baseline)

| SLO | Target | Basis |
|---|---|---|
| Authorization availability | ≥ 99.9% | Phase 20 baseline: 0 errors at 100 CC |
| p95 authorization latency | ≤ 400 ms | Phase 20 baseline: ~331 ms |
| p99 authorization latency | ≤ 500 ms | Phase 20 baseline: ~350 ms |
| Unauthorized executions | **= 0** | Security invariant, non-negotiable |
| Duplicate executions | **= 0** | Security invariant, non-negotiable |
| Unsafe ALLOWs | **= 0** | Security invariant, non-negotiable |

The last three are not performance targets. They are **security invariants**.

## 4. Trace Span Tree

```
POST /evaluate                           [root span]
  │
  ├── sentinel.idempotency.check         [redis SET NX + GET]
  │
  ├── sentinel.kafka.publish             [send_and_wait to intents.inbound]
  │
  ├── sentinel.redis.poll                [xread block=5000ms on reply stream]
  │     │
  │     └── [continues in worker process — linked via traceparent]
  │
  └── sentinel.response

worker.evaluate                          [child of API root, via traceparent]
  │
  ├── sentinel.feature.extraction        [extract_features(context)]
  │
  ├── sentinel.xgboost.inference         [xgb.DMatrix + model.predict]
  │
  ├── sentinel.semantic.evaluate         [SimulatedSemanticClient]
  │
  ├── sentinel.policy.evaluate           [PolicyEngine.evaluate]
  │
  ├── sentinel.capability.issue          [token signing, if ALLOW]
  │
  ├── sentinel.kafka.reply_publish       [send_and_wait to intents.evaluated]
  │
  └── sentinel.redis.reply_write         [xadd reply:{intent_id}]
```

Trace context is propagated via a `traceparent` field in the Kafka message JSON payload (W3C Trace Context format). No Kafka header manipulation required.

## 5. Health Endpoint Contract

| Endpoint | Purpose | Affects routing? | Fail-closed impact? |
|---|---|---|---|
| `GET /health/live` | Is the process alive? | No | No |
| `GET /health/ready` | Can this instance authorize safely? | **Yes** — load balancers use this | No — returns 503, never bypasses fail-closed |
| `GET /health/dependencies` | Detailed dependency status + latency | No | No |

**Invariant:** Health checks must never accidentally change authorization semantics. A degraded Redis health check must not trigger an ALLOW decision.

---

## 6. Observability Isolation Invariant

> If any observability component fails (Prometheus scrape, OTLP export, Grafana, Jaeger, logging handler, metrics increment), the authorization path must continue to operate with correct fail-closed semantics.

This is verified by `test_observability_cannot_affect_authorization` in the Phase 21 chaos suite.

```
Redis / Kafka / Postgres / Policy failure → FAIL CLOSED (authorization invariant)
Prometheus / Grafana / Jaeger / Logger failure → silent, authorization unaffected
```
